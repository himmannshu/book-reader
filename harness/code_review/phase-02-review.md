## Bugs and findings

**F1 (medium-low, latent). When the visible pages alone exceed the canvas budget, every small scroll
redraws every page.**
In this regime the pixel ratio comes from the total size of the visible pages
(src/viewer/layout.ts:130-139). That total changes whenever one page enters or leaves the viewport. The
viewer then releases every slot whose drawn ratio differs from the new plan (src/viewer/viewer.ts:160;
line 175 on current HEAD), so all visible pages go blank and draw again.
Repro: Chromium or WebKit, DPR 2, viewport 1280×10000, open heavy-600-v1, wait 1.5 s, then scroll by
40 px per frame-pair 60 times (2400 px, about 2 pages). I counted 74 transitions to `rendering`; about
2 to 4 are expected. One second and a half later, WebKit still had only 8 of 9 visible pages drawn. A
steady 2000 px/s scroll showed 33% blank frames in Chromium and 67% in WebKit, against 0% and 1% at
1280×720 (part of that is simply the cost of a huge viewport).
No real screen reaches this today: it needs about 6 or more full-width letter pages visible at DPR 2.
It will become real once zoom-out or multi-page views arrive (phase 10). Expected: the resolution
changes rarely. For example, round the ratio to coarse steps, add hysteresis, or redraw only when the
ratio must go down to stay in budget.

**F2 (test quality). The memory checks pass whether or not the cap works.**
- e2e/perf/reader.perf.ts:41-45 measures 67.1 MB, which is just 2 visible plus 2 overscan letter pages
  at overscan 1, far below 96 MB. With the overscan budget check removed from `planRender`, this
  benchmark still passes at 67.1 MB. Only the unit test catches it.
- The B2 e2e test (e2e/open-pdf.spec.ts:193) checks that every visible page is drawn but not the
  "memory cap holds" half of contract item 8.
- The reduced-resolution path (visible pages over budget) has a unit test but no browser test. A tall
  viewport, or a small `maxCanvasBytes` passed to the viewer, would cover it.

**F3 (nit). `src/core/perf-marks.ts` uses the `performance` global.** AGENTS.md says src/core contains
"No browser APIs". `performance` exists in Node too, so this is borderline, but timing marks are a
viewer and UI concern. `page:rendered` marks also build up without limit while one book stays open.
They are cleared only when another book opens. That is small, but it grows with every page drawn
during a long reading session.

**F4 (nit). A stale test name.** e2e/open-pdf.spec.ts:31 is still titled "keeps at most 8 canvases". The
8-page cap no longer exists; the test now only holds because overscan is 1 at 720 px. The name and
the assertion describe a rule the viewer no longer has.
