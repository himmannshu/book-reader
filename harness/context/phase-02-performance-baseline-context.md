# Phase 02 context: performance baseline

Material decisions only. Measurements are in harness/build-log.md.

## What is measured, and how

- The app records User Timing marks (src/core/perf-marks.ts): `book:open-start`, `book:opened`,
  and `page:rendered` with `{ pageIndex }`. They are cleared on each new open. The same marks
  show up in browser DevTools for hands-on profiling.
- The benchmarks (e2e/perf/reader.perf.ts) have their own config, playwright.perf.config.ts:
  Chromium and WebKit, device scale factor 2, one worker, the median of 3 runs after one warm-up.
  - First page: open-start → page 1 drawn.
  - Jump: scroll to pages at 90%, 50% and 75% of the book → that page drawn.
  - Scroll: 3 s at 2000 px/s; p95 of the time between frames, plus the % of frames showing an
    undrawn visible page.
  - Memory: the largest total canvas size seen at 30 positions spread over the whole book.
- Heavy book: generated by scripts/generate-heavy-fixture.mjs (heavy-600-v1, 57.8 MB, gitignored)
  and rebuilt by the global setup when missing. To change its content, bump the `v1` in the name.
- Limitation: the scroll metrics did not catch a 300 ms per-page delay. Overscan pre-draws ahead
  of the reader at this scroll speed. First-page and jump times do catch it (build log,
  negative check).

## Budgets and CI policy

- e2e/perf/budgets.json holds the user-agreed limits for the M2, plus `ciTimeMultiplier: 4` and
  `ciEnforcedProjects: ["perf-chromium"]`.
- In CI only Chromium is enforced, with the time budgets ×4. WebKit is measured and uploaded but
  not enforced (contract amendment 1). Linux CI WebKit was about 8× slower on time and about 14×
  on frames, with 75% blank frames, so it measures the runner, not the app.
- Local `scripts/verify.sh` enforces both browsers strictly.
- Budget checks are soft, so every metric is recorded even when an earlier one fails.
- Change budgets only with the user's agreement (AGENTS.md).

## Memory planner replaces the 8-page cap (fixes review finding B2)

- `planRender` (src/viewer/layout.ts) always includes every visible page. It adds overscan only
  while the total canvas bytes stay ≤ `maxCanvasBytes` (96 MB). If the visible pages alone
  exceed that, it lowers the pixel ratio instead of leaving pages blank.
- The viewer frees canvases before allocating new ones, and draws visible pages before
  overscan. The draw order matters: drawing in plain index order made WebKit jumps about 50%
  slower (median 129 ms vs 88 ms).

## Findings to carry forward

- On a real 24 MB book (DDIA), first page took 462 ms in Chromium and 384 ms in WebKit, against
  the 400 ms product target and about 3× the heavy fixture. Jump, scroll and memory matched the
  fixture. The cause is not measured yet. Splitting `book:open-start → book:opened → page:rendered`
  is the first step.

- WebKit p95 frame time on the M2 is 28–33 ms, right at the 34 ms product target, because PDF.js
  draws on the main thread. The candidate fix is drawing off the main thread (OffscreenCanvas
  in a worker) or a PDFium engine behind the same interface (D3). Either is a user decision.
- Real iPad and iPhone performance is not measured. There is no device automation; it is a
  manual check for later.
